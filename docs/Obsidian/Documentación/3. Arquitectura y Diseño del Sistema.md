## 3.2 Representación Arquitectónica

HELIOS sigue una arquitectura de **tres capas** con un backend gestionado (BaaS — Backend as a Service) provisto por Supabase:

```
┌─────────────────────────────────────────────────────┐
│                  CAPA DE PRESENTACIÓN                │
│           React + TypeScript (Web Responsive)        │
│      Portal Paciente · Dashboard Médico · Admin      │
└─────────────────────────┬───────────────────────────┘
                          │ HTTPS / WSS
                          ▼
┌─────────────────────────────────────────────────────┐
│                  CAPA DE SERVICIOS                   │
│                    SUPABASE                          │
│                                                      │
│  PostgREST API  │  Auth  │  Realtime  │  Edge Fns   │
└─────────────────────────┬───────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────┐
│                  CAPA DE DATOS                       │
│              PostgreSQL (Supabase)                   │
│                                                      │
│  pacientes · medicos · sedes · citas                 │
│  disponibilidad · notificaciones · sync_logs         │
└─────────────────────────────────────────────────────┘
```

## 3.3 Objetivos y Restricciones Arquitectónicas

### Objetivos

|Objetivo|Decisión arquitectónica|
|---|---|
|Sincronización en tiempo real entre sedes|Supabase Realtime con canales PostgreSQL|
|Sin backend propio para reducir complejidad|BaaS con Supabase (PostgREST + Edge Functions)|
|Seguridad a nivel de datos|Row Level Security (RLS) en todas las tablas|
|Notificaciones automáticas sin servidor propio|Supabase Edge Functions (Deno) con cron|
|Despliegue continuo automatizado|Railway + GitHub Actions|
|Calidad de código verificada|SonarQube Community en pipeline CI/CD|

### Restricciones

- Sin app móvil nativa — web responsive cubre el caso de uso
- Supabase free tier: 500MB base de datos, 2GB transferencia mensual
- Sin integración real con API de CSS/MINSA en esta fase
- Proveedor SMS panameño pendiente de definición
- Equipo de 5 personas con tiempo limitado por el calendario académico

## 3.6 Vista de Procesos — Comunicación entre Capas

### Flujo de una petición normal (agendamiento)

```
Paciente (navegador)
    │
    │  1. POST /rest/v1/citas (HTTPS)
    ▼
Supabase PostgREST API
    │
    │  2. Valida JWT token
    │  3. Aplica políticas RLS
    │  4. Ejecuta INSERT en PostgreSQL
    ▼
PostgreSQL
    │
    │  5. Dispara evento Realtime
    ▼
Supabase Realtime
    │
    │  6. Broadcast a suscriptores del canal citas-sync
    ▼
Frontend del Médico (WebSocket)
    │
    │  7. Actualiza agenda en menos de 5 segundos
    ▼
Médico ve la nueva cita en pantalla
```

### Flujo de notificación automática (cron)

```
Supabase Cron (cada hora)
    │
    │  1. Dispara Edge Function enviar-recordatorio
    ▼
Edge Function (Deno)
    │
    │  2. Consulta citas en próximas 24h/1h
    │  3. Verifica que no se haya enviado ya
    │  4. Determina canal preferido del paciente
    ▼
    ├── App Web → Supabase Realtime → Frontend paciente
    ├── Correo  → Resend API → Bandeja del paciente
    └── SMS     → SMS Gateway → Teléfono del paciente
    │
    │  5. Registra estado en tabla notificaciones
    ▼
Log guardado en PostgreSQL
```

### Flujo de sincronización entre sedes

```
Evento en tabla citas (INSERT/UPDATE/DELETE)
    │
    │  1. PostgreSQL dispara cambio a Realtime
    ▼
Supabase Realtime — canal citas-sync
    │
    │  2. Broadcast a todos los clientes suscritos
    ▼
Frontends de todas las sedes activas
    │
    │  3. Cada sede confirma recepción
    │  4. Si falla → reintento exponencial (1s, 2s, 4s)
    │  5. Si 3 fallos → alerta al admin
    ▼
sync_logs actualizado con resultado
```

## 3.9 Patrones de Diseño Aplicados

|Patrón|Dónde se aplica|Por qué|
|---|---|---|
|**Repository Pattern**|Archivos `*.service.ts`|Centraliza las llamadas a Supabase, los componentes no tocan la BD directamente|
|**Observer Pattern**|Supabase Realtime|El frontend se suscribe a cambios y reacciona automáticamente|
|**Retry Pattern**|Sincronización entre sedes|Reintentos con espera exponencial ante fallos de red|
|**Singleton**|`lib/supabase.ts`|Una sola instancia del cliente Supabase en toda la app|
|**Role-Based Access Control**|RLS en Supabase|Cada rol (paciente, médico, admin) solo accede a lo que le corresponde|
|**Event-Driven**|Realtime + Edge Functions|Los cambios en BD disparan eventos que actualizan UI y envían notificaciones|
|**BFF — Backend for Frontend**|PostgREST API|El frontend consulta datos con queries específicas sin lógica de negocio en el cliente|

## 3.10 Seguridad Arquitectónica

### Capas de seguridad

```
1. TRANSPORTE
   └── HTTPS/TLS 1.2+ en todas las comunicaciones
   └── WSS (WebSocket Secure) para Realtime

2. AUTENTICACIÓN
   └── Supabase Auth con JWT tokens
   └── Tokens expiran cada 8 horas
   └── Máximo 5 intentos fallidos → bloqueo 15 min

3. AUTORIZACIÓN
   └── RLS activo en todas las tablas
   └── Políticas basadas en auth.uid() y rol
   └── Ninguna tabla accesible sin autenticación (excepto sedes y médicos públicos)

4. DATOS EN REPOSO
   └── AES-256 gestionado por Supabase
   └── Contraseñas con bcrypt (Supabase Auth)

5. DATOS EN TRÁNSITO
   └── sync_logs no contiene datos personales
   └── Cédula y correo nunca aparecen en logs
   └── Cumplimiento Ley 81 de Panamá

6. CÓDIGO
   └── SonarQube Community analiza vulnerabilidades
   └── 0 vulnerabilidades críticas antes de cada deploy
```

## 3.11 Calidad Arquitectónica (ISO/IEC 25010)

|Característica|Decisión arquitectónica que la garantiza|
|---|---|
|**Funcionalidad**|PostgREST API + RLS garantiza que cada rol accede solo a lo que corresponde|
|**Rendimiento**|Supabase Realtime evita polling, respuestas en tiempo real|
|**Fiabilidad**|Retry pattern con espera exponencial en sincronización|
|**Usabilidad**|Diseño responsivo + WCAG 2.1 AA + SUS ≥ 75|
|**Seguridad**|JWT + RLS + HTTPS + SonarQube + Ley 81 Panamá|
|**Mantenibilidad**|Módulos independientes + Repository pattern + pruebas automatizadas|
|**Portabilidad**|Web responsive, sin dependencia de OS ni dispositivo específico|
|**Compatibilidad**|PostgREST API estándar, compatible con cualquier cliente HTTP|
