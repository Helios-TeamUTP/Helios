## 2.1 Introducción

### Propósito

Este documento especifica los requisitos funcionales y no funcionales del sistema HELIOS. Está dirigido al equipo de desarrollo, al equipo de QA y a la profesora evaluadora. Sirve como contrato técnico entre lo que el sistema debe hacer y cómo debe comportarse.

### Alcance del sistema

HELIOS cubre el ciclo completo de gestión de citas médicas para la red de policlínicas gubernamentales de Panamá. En el alcance del Parcial 1 se incluyen los módulos de agendamiento, cancelación, sincronización entre sedes y notificaciones. Los módulos de expediente médico, directorio completo y pagos en línea son visión futura.

## 2.2 Descripción General del Sistema

### Contexto

HELIOS opera como una aplicación web institucional del Gobierno de Panamá. Los usuarios acceden desde cualquier navegador sin instalación. El sistema se conecta a Supabase como backend, gestiona autenticación con roles diferenciados (paciente, médico, administrador) y sincroniza información entre las bases de datos de todas las sedes en tiempo real.

### Funciones principales

1. Registro y autenticación de pacientes y médicos
2. Agendamiento de citas médicas por flujo guiado
3. Cancelación y reprogramación de citas
4. Sincronización en tiempo real entre sedes
5. Envío automático de notificaciones y recordatorios
6. Gestión de agenda médica en tiempo real
7. Consulta de historial de citas

### Usuarios del sistema

|Usuario|Descripción|
|---|---|
|Paciente|Ciudadano panameño que agenda citas|
|Médico|Profesional que consulta su agenda|
|Administrador|Personal de sede que monitorea el sistema|
|Sistema|Procesos automáticos (cron, notificaciones, sync)|

### Restricciones generales

- Idioma: Español (Panamá)
- Navegadores soportados: Chrome, Firefox, Safari, Edge (versiones actuales)
- Dispositivos: Desktop y móvil (web responsive)
- Cumplimiento: Ley 81 de Panamá — Protección de Datos Personales
- Accesibilidad: WCAG 2.1 nivel AA

## 2.3 Requisitos Funcionales

### Módulo 00 — Autenticación y Registro

---

**RF-01: Registro de paciente**

- **Descripción:** El sistema debe permitir a un ciudadano crear una cuenta usando su cédula panameña o pasaporte
- **Prioridad:** ALTA
- **Datos requeridos:**
    - Nombre completo
    - Cédula panameña (formato: X-XXX-XXXX) o pasaporte
    - Fecha de nacimiento
    - Sexo
    - Número telefónico
    - Correo electrónico
    - Contraseña (mínimo 8 caracteres, 1 mayúscula, 1 número)
- **Validaciones:**
    - Cédula no debe estar previamente registrada
    - Correo no debe estar previamente registrado
    - Formato de cédula panameña válido
- **Resultado:** Cuenta creada, correo de verificación enviado

---

**RF-02: Verificación de cuenta**

- **Descripción:** El sistema debe verificar la identidad del paciente antes de permitir el acceso completo
- **Prioridad:** ALTA
- **Flujo:** Registro → Correo de verificación → Click en link → Cuenta activa
- **Alternativa:** Verificación por SMS si el paciente no tiene correo

---

**RF-03: Inicio de sesión**

- **Descripción:** El sistema debe autenticar a los usuarios con correo/cédula y contraseña
- **Prioridad:** ALTA
- **Roles:** Paciente / Médico / Administrador
- **Validaciones:**
    - Máximo 5 intentos fallidos → bloqueo temporal de 15 minutos
    - Sesión expira después de 8 horas de inactividad
- **Opcional:** Doble factor de autenticación por SMS

---

**RF-04: Recuperación de contraseña**

- **Descripción:** El usuario puede solicitar un enlace de recuperación a su correo registrado
- **Prioridad:** MEDIA
- **Flujo:** Solicitar → Correo con link → Nueva contraseña → Confirmación

---

**RF-05: Verificación de cobertura**

- **Descripción:** El sistema debe verificar el tipo de cobertura del paciente al registrarse o agendar
- **Prioridad:** MEDIA
- **Opciones:**
    - Asegurado CSS (verificación por número de cédula)
    - Beneficiario MINSA (atención gratuita)
    - Pago particular en clínica
- **Resultado:** Tipo de cobertura guardado en perfil del paciente

---

### Módulo 01 — Agendamiento de Citas

---

**RF-06: Selección de sede**

- **Descripción:** El paciente debe poder seleccionar la policlínica donde desea ser atendido
- **Prioridad:** ALTA
- **Datos mostrados por sede:**
    - Nombre de la sede
    - Provincia y dirección
    - Teléfono
    - Especialidades disponibles
- **Filtro:** Por provincia (Panamá, Colón, Chiriquí, Veraguas, Coclé, Herrera, Los Santos, Darién, Bocas del Toro, Panamá Oeste)

---

**RF-07: Selección de especialidad**

- **Descripción:** El paciente debe poder seleccionar la especialidad médica deseada según disponibilidad en la sede elegida
- **Prioridad:** ALTA
- **Especialidades iniciales:**
    - Medicina General
    - Pediatría
    - Cardiología
    - Dermatología
    - Ginecología
    - Odontología
    - Ortopedia
- **Validación:** Solo mostrar especialidades con al menos un médico disponible en esa sede

---

**RF-08: Selección de médico**

- **Descripción:** El paciente debe poder elegir entre los médicos disponibles para la especialidad seleccionada
- **Prioridad:** ALTA
- **Datos mostrados por médico:**
    - Nombre completo
    - Especialidad
    - Sede
    - Indicador de disponibilidad (disponible hoy / próxima disponibilidad)
- **Restricción:** No mostrar calificaciones ni reseñas (sistema gubernamental, neutral)

---

**RF-09: Selección de fecha y hora**

- **Descripción:** El paciente debe poder ver y seleccionar un horario disponible del médico elegido
- **Prioridad:** ALTA
- **Comportamiento:**
    - Mostrar calendario con días disponibles resaltados
    - Al seleccionar día, mostrar slots de tiempo disponibles
    - Slots ocupados no son seleccionables
    - El sistema valida disponibilidad en tiempo real antes de confirmar
- **Slots predeterminados:** Cada 30 minutos entre 7:00 AM y 4:00 PM

---

**RF-10: Confirmación de cita**

- **Descripción:** El paciente debe revisar y confirmar el resumen de su cita antes de registrarla
- **Prioridad:** ALTA
- **Datos del resumen:**
    - Sede
    - Especialidad
    - Médico
    - Fecha y hora
    - Tipo de cobertura
    - Canal de notificación preferido
- **Resultado:** Cita registrada en Supabase, código único generado, confirmación enviada al paciente

---

**RF-11: Comprobante de cita**

- **Descripción:** El sistema debe generar un comprobante descargable al confirmar la cita
- **Prioridad:** MEDIA
- **Formato:** PDF con código de cita, QR y datos del agendamiento
- **Canales:** Descarga directa + envío por correo

---

**RF-12: Vista de agenda del médico**

- **Descripción:** El médico debe poder ver su agenda del día actualizada en tiempo real
- **Prioridad:** ALTA
- **Datos por cita:**
    - Hora
    - Nombre del paciente
    - Tipo de consulta
    - Estado (confirmada, en espera, cancelada)
- **Actualización:** Automática via Supabase Realtime en menos de 5 segundos
- **Filtros:** Por fecha, por estado

---

### Módulo 02 — Cancelación y Reprogramación

---

**RF-13: Ver citas activas**

- **Descripción:** El paciente debe poder ver todas sus citas activas desde "Mis Citas"
- **Prioridad:** ALTA
- **Estados visibles:** Confirmada / Pendiente / Cancelada / Finalizada
- **Orden:** Fecha ascendente (próximas primero)

---

**RF-14: Cancelar cita**

- **Descripción:** El paciente puede cancelar una cita confirmada
- **Prioridad:** ALTA
- **Regla de negocio RR-01:** Solo se puede cancelar con mínimo 24 horas de anticipación
- **Flujo:**
    1. Seleccionar cita → Cancelar
    2. Sistema valida tiempo mínimo
    3. Seleccionar motivo de cancelación
    4. Confirmar → Estado cambia a "cancelada"
    5. Slot liberado en agenda del médico
    6. Médico notificado
- **Motivos de cancelación:** Emergencia, no puede asistir, cambio de médico, error en agendamiento, otro

---

**RF-15: Reprogramar cita**

- **Descripción:** El paciente puede reprogramar una cita sin cancelar y crear una nueva manualmente
- **Prioridad:** ALTA
- **Flujo:**
    1. Seleccionar cita → Reprogramar
    2. Sistema marca cita anterior como "reprogramada"
    3. Redirige a flujo de agendamiento pre-cargado (sede, especialidad, médico)
    4. Paciente selecciona nueva fecha y hora
    5. Nueva cita registrada como "confirmada"
    6. Médico notificado del cambio
- **Restricción:** Se puede cambiar fecha/hora. Cambio de médico o sede inicia flujo nuevo completo

---

**RF-16: Historial de citas**

- **Descripción:** El paciente puede ver el historial completo de sus citas pasadas
- **Prioridad:** MEDIA
- **Filtros:** Por estado, por fecha, por médico
- **Orden:** Fecha descendente (más reciente primero)

---

### Módulo 03 — Sincronización entre Sedes

---

**RF-17: Propagación automática de cambios**

- **Descripción:** Cualquier cambio en la tabla de citas debe propagarse automáticamente a todas las sedes
- **Prioridad:** ALTA
- **Eventos sincronizados:** INSERT, UPDATE, DELETE en tabla `citas`
- **Tiempo máximo:** 3 segundos en el 99% de los casos
- **Mecanismo:** Supabase Realtime con canal `citas-sync`

---

**RF-18: Reintentos automáticos**

- **Descripción:** Si una sincronización falla, el sistema debe reintentarla automáticamente
- **Prioridad:** ALTA
- **Comportamiento:**
    - Reintento 1: después de 1 segundo
    - Reintento 2: después de 2 segundos
    - Reintento 3: después de 4 segundos
    - Si los 3 fallan: alerta al administrador
- **Log:** Cada intento registrado en `sync_logs`

---

**RF-19: Registro de logs de sincronización**

- **Descripción:** El sistema debe registrar cada operación de sincronización con su resultado
- **Prioridad:** ALTA
- **Campos del log:** sede origen, sede destino, tabla, operación, estado, intentos, error si aplica, timestamp
- **Acceso:** Solo administradores

---

**RF-20: Dashboard de sincronización**

- **Descripción:** El administrador debe tener un panel de monitoreo del estado de sincronización
- **Prioridad:** MEDIA
- **Contenido:**
    - Estado de cada sede (sincronizada / con fallos)
    - Últimas 50 sincronizaciones
    - Filtros por sede y estado
    - Indicador de salud del sistema

---

**RF-21: Alerta de fallo crítico**

- **Descripción:** El sistema debe notificar al administrador cuando una sincronización falle después de 3 intentos
- **Prioridad:** ALTA
- **Canal:** Notificación en el dashboard + correo al administrador de la sede
- **Información:** Sede afectada, tipo de operación, hora del fallo, número de intentos

---

### Módulo 04 — Notificaciones y Recordatorios

---

**RF-22: Recordatorio 24 horas antes**

- **Descripción:** El sistema debe enviar un recordatorio al paciente 24 horas antes de su cita
- **Prioridad:** ALTA
- **Mecanismo:** Edge Function con cron cada hora
- **Canales:** App web (Realtime), correo (Resend), SMS (proveedor panameño)
- **Contenido:** Médico, especialidad, sede, fecha, hora, link de confirmación de asistencia

---

**RF-23: Recordatorio 1 hora antes**

- **Descripción:** El sistema debe enviar un recordatorio final al paciente 1 hora antes de su cita
- **Prioridad:** ALTA
- **Validación:** No enviar si ya fue cancelada o reprogramada
- **Contenido:** Igual al recordatorio de 24h + "Ya es hora de salir"

---

**RF-24: Confirmación de asistencia**

- **Descripción:** El paciente debe poder confirmar su asistencia desde la notificación
- **Prioridad:** MEDIA
- **Flujo:** Notificación → Botón "Confirmar asistencia" → Estado actualizado → Médico notificado
- **Registro:** Timestamp de confirmación guardado en `citas`

---

**RF-25: Notificación de cancelación o cambio**

- **Descripción:** El paciente debe recibir notificación inmediata si su cita fue cancelada o reprogramada
- **Prioridad:** ALTA
- **Tiempo:** Menos de 30 segundos tras el cambio
- **Contenido:** Motivo del cambio (si disponible) + link para reprogramar

---

**RF-26: Centro de notificaciones**

- **Descripción:** El paciente debe tener un centro donde ver todas sus notificaciones
- **Prioridad:** MEDIA
- **Contenido:** Lista de notificaciones con tipo, fecha y estado (leída / no leída)
- **Actualización:** Tiempo real via Supabase Realtime

---

**RF-27: Preferencias de notificación**

- **Descripción:** El paciente puede configurar su canal preferido de notificación
- **Prioridad:** MEDIA
- **Opciones:** App web / Correo electrónico / SMS
- **Persistencia:** Guardado en perfil del paciente en Supabase

## 2.5 Requisitos No Funcionales

### Rendimiento

**RNF-01: Tiempo de respuesta general**

- El 95% de las peticiones al sistema deben responderse en menos de 2 segundos bajo carga normal

**RNF-02: Carga concurrente**

- El sistema debe soportar 5,000 usuarios concurrentes sin degradación del servicio
- Prueba: 100 usuarios simulados con script Python, 95% bajo 2 segundos

**RNF-03: Sincronización entre sedes**

- El 99% de las sincronizaciones deben completarse en menos de 3 segundos

**RNF-04: Notificaciones por evento**

- Las notificaciones por cancelación o cambio deben enviarse en menos de 30 segundos

---

### Seguridad

**RNF-05: Autenticación**

- Autenticación gestionada por Supabase Auth con tokens JWT
- Sesiones expiran a las 8 horas de inactividad

**RNF-06: Autorización por roles**

- Row Level Security (RLS) activo en todas las tablas
- Paciente solo ve sus propios datos
- Médico solo ve sus citas
- Administrador accede a logs y dashboard de sincronización

**RNF-07: Cifrado**

- Todas las comunicaciones bajo HTTPS (TLS 1.2 mínimo)
- Datos en reposo cifrados por Supabase (AES-256)
- Contraseñas nunca almacenadas en texto plano (bcrypt via Supabase Auth)

**RNF-08: Protección de datos sensibles**

- Los logs de sincronización no deben contener cédula, correo ni datos personales
- Cumplimiento con Ley 81 de Panamá — Protección de Datos Personales

**RNF-09: Límite de intentos**

- Máximo 5 intentos de login fallidos → bloqueo temporal de 15 minutos

**RNF-10: Vulnerabilidades de código**

- SonarQube Community debe reportar 0 vulnerabilidades críticas antes de cada release

---

### Usabilidad

**RNF-11: Facilidad de uso**

- El flujo de agendamiento debe completarse en menos de 3 minutos para un usuario nuevo
- Puntaje SUS ≥ 75 sobre 100 en muestra de médicos y pacientes

**RNF-12: Accesibilidad**

- La interfaz debe cumplir WCAG 2.1 nivel AA
- Contraste mínimo de 4.5:1 en texto
- Navegación completa por teclado
- Etiquetas ARIA en formularios

**RNF-13: Diseño responsivo**

- La interfaz debe funcionar correctamente en pantallas desde 375px (móvil) hasta 1920px (desktop)
- Sin necesidad de zoom horizontal en ningún dispositivo

**RNF-14: Idioma**

- Todo el contenido visible al usuario en Español (Panamá)
- Formato de fecha: DD de mes de YYYY (ej: 10 de junio de 2026)
- Formato de hora: 12 horas con AM/PM

---

### Fiabilidad

**RNF-15: Disponibilidad**

- El sistema debe estar disponible el 99% del tiempo (máximo 7.3 horas de downtime al año)

**RNF-16: Recuperación ante fallos**

- Ante fallo de sincronización, el sistema reintenta automáticamente hasta 3 veces
- Ante fallo total, muestra mensaje de error claro al usuario sin perder datos ingresados

---

### Mantenibilidad

**RNF-17: Modularidad**

- El código debe estar organizado por módulos independientes
- Un cambio en el módulo de notificaciones no debe afectar el módulo de agendamiento

**RNF-18: Cobertura de pruebas**

- Cada módulo debe tener pruebas funcionales con Vitest
- Las pruebas deben correr automáticamente en el pipeline CI/CD antes de cada deploy

**RNF-19: Documentación de código**

- Todas las funciones de servicios deben tener comentarios JSDoc
- El README del repositorio debe mantenerse actualizado con cada sprint

## 2.6 Requisitos de Interfaz

### Interfaz de usuario

**RI-01: Identidad visual gubernamental**

- Colores primarios: Azul #003087, Rojo #CE1126, Blanco #FFFFFF
- Colores secundarios: Gris claro #F5F5F5, Gris texto #333333
- Fuente: Sistema nativo o sans-serif institucional
- Logo HELIOS en header izquierdo
- Sello del Gobierno de Panamá en header derecho

**RI-02: Navegación principal (paciente)**

- Inicio
- Agendar Cita
- Mis Citas
- Notificaciones
- Mi Perfil

**RI-03: Navegación principal (médico)**

- Resumen
- Mi Agenda
- Pacientes
- Configuración

**RI-04: Navegación principal (administrador)**

- Dashboard
- Sincronización
- Sedes
- Reportes

### Interfaz con Supabase

**RI-05:** El sistema se comunica con Supabase via PostgREST API para operaciones CRUD **RI-06:** El sistema usa Supabase Realtime para actualizaciones en tiempo real **RI-07:** El sistema usa Supabase Auth para autenticación y gestión de sesiones **RI-08:** El sistema usa Supabase Edge Functions para el envío de notificaciones automáticas

### Interfaz con servicios externos

**RI-09:** Resend API para envío de correos transaccionales **RI-10:** Proveedor SMS panameño para recordatorios por mensaje de texto (por definir) **RI-11:** Railway para despliegue y hosting del frontend
